Declare your uptime monitors and status pages next to the services they watch. `pulumi preview` shows exactly what will change, and `pulumi up` applies it.

<Callout type="info">
  **Package**: `@databuddy/pulumi` | **Requires**: Pulumi CLI and
  `@pulumi/pulumi` 3.216 or newer, Pulumi's `nodejs` runtime
</Callout>

## Setup

<Steps>
<Step>

### Install the package

<CodeBlock language="bash">
  {`npm install @databuddy/pulumi`}
</CodeBlock>

The provider runs in TypeScript and JavaScript programs, CommonJS or ESM. Bun works as the package manager, but Pulumi can't run dynamic providers under `runtime: bun`, so keep `runtime: nodejs` in `Pulumi.yaml`.

</Step>
<Step>

### Create an API key

Open [Organization Settings → API Keys](https://app.databuddy.cc/organizations/settings#api-keys) and create a key with these scopes:

- `read:monitors`
- `write:monitors`
- `read:status_pages`
- `write:status_pages`

Monitors and status pages are created in the key's organization.

</Step>
<Step>

### Add the key to your stack

<CodeBlock language="bash">
  {`pulumi config set --secret databuddy:apiKey dbdy_...`}
</CodeBlock>

Pulumi encrypts the key in your stack config. In CI you can export `DATABUDDY_API_KEY` instead.

</Step>
</Steps>

## Quick Start

<CodeBlock language="tsx">
  {`import * as pulumi from "@pulumi/pulumi";
import { StatusPage, StatusPageMonitor, UptimeMonitor } from "@databuddy/pulumi";

const api = new UptimeMonitor("api", {
  url: "https://api.example.com/health",
  name: "API",
  granularity: "minute",
});

const status = new StatusPage("status", {
  name: "Example",
  slug: \`acme-\${pulumi.getStack()}\`,
  theme: "dark",
});

new StatusPageMonitor("api-on-status", {
  statusPageId: status.id,
  monitorId: api.id,
  displayName: "API",
  hideUrl: true,
});`}
</CodeBlock>

Run `pulumi up` and the monitor starts checking, the status page goes live, and the API shows up on it. Replace `acme` with your own name: status page slugs are unique across every Databuddy account.

## Resources

### UptimeMonitor

Checks a URL on a schedule and records status, latency, and SSL details. See [Uptime Monitoring](/docs/uptime) for what each check measures.

| Argument | Type | Default | Description |
|----------|------|---------|-------------|
| `url` | `string` | Required | `http` or `https` URL to check. Changing it replaces the monitor |
| `granularity` | `string` | Required | How often to check: `minute`, `five_minutes`, `ten_minutes`, `thirty_minutes`, `hour`, `six_hours`, `twelve_hours`, or `day` |
| `name` | `string` | - | Name shown in the dashboard and on status pages |
| `timeout` | `number` | - | Request timeout in milliseconds, from `1000` to `120000` |
| `cacheBust` | `boolean` | `false` | Add a cache-busting query parameter to every check |
| `paused` | `boolean` | `false` | Stop checking without deleting the monitor |
| `websiteId` | `string` | - | Link the monitor to a tracked website. Changing it replaces the monitor |

Every argument is also available as an output, along with the monitor's `id`.

### StatusPage

A public, branded status page.

| Argument | Type | Default | Description |
|----------|------|---------|-------------|
| `name` | `string` | Required | Page title, up to 120 characters |
| `slug` | `string` | Required | URL slug: lowercase letters, numbers, and dashes, up to 100 characters. Unique across every Databuddy account |
| `description` | `string` | - | Short description, up to 500 characters |
| `logoUrl` | `string` | - | `https` URL of your logo |
| `faviconUrl` | `string` | - | `https` URL of your favicon |
| `websiteUrl` | `string` | - | `https` link back to your site |
| `supportUrl` | `string` | - | `https` link to your support page |
| `theme` | `string` | `system` | `system`, `light`, or `dark` |

Outputs include every argument plus `organizationId`.

### StatusPageMonitor

Puts a monitor on a status page and controls how it is shown.

| Argument | Type | Default | Description |
|----------|------|---------|-------------|
| `statusPageId` | `string` | Required | The status page. Changing it moves the entry |
| `monitorId` | `string` | Required | The monitor to show. Changing it swaps the entry |
| `displayName` | `string` | Monitor name | Name shown on the page, up to 120 characters |
| `order` | `number` | `0` | Position on the page, lowest first |
| `hideUrl` | `boolean` | `false` | Hide the monitored URL |
| `hideUptimePercentage` | `boolean` | `false` | Hide the uptime percentage |
| `hideLatency` | `boolean` | `false` | Hide response times |

## Dashboard Edits and Drift

Your program is the source of truth. If someone edits a monitor or status page in the dashboard:

- `pulumi refresh` (or `pulumi up --refresh`) shows the change
- The next `pulumi up` puts it back to what your code says

To let the dashboard own a field, list it in `ignoreChanges`. For example, so on-call can pause a monitor during an incident without the next deploy resuming it:

<CodeBlock language="tsx">
  {`new UptimeMonitor(
  "checkout",
  { url: "https://shop.example.com/checkout", granularity: "minute" },
  { ignoreChanges: ["paused"] }
);`}
</CodeBlock>

## Replacements

Some changes can't be made in place, so Pulumi creates a new resource and removes the old one:

- **Monitor `url` or `websiteId`**: the new monitor starts with a fresh check history. Point any dashboard alerts at the new monitor, and re-add status page entries that were created in the dashboard rather than in code. Pulumi creates the new monitor first unless it keeps the same URL or website, which have to be freed before they can be reused.
- **`StatusPageMonitor` page or monitor**: the entry is recreated, and incidents that listed it stop showing it.

`pulumi preview` marks these as `replace`, so you see them before anything changes.

## Uniqueness

- Status page slugs are unique across every Databuddy account
- Within an organization, monitor URLs are unique and a website can have only one monitor

If several stacks share an organization, give each one its own slugs, URLs, and websites. A URL or slug has to be released in one `pulumi up` before another resource can take it in the next.

When you rename a resource or move it under a parent, add `aliases` so Pulumi updates the existing monitor or page instead of trying to create a second one with the same URL or slug:

<CodeBlock language="tsx">
  {`new UptimeMonitor(
  "api-health",
  { url: "https://api.example.com/health", granularity: "minute" },
  { aliases: [{ name: "api" }] }
);`}
</CodeBlock>

## Running in CI

Store the key as a CI secret and pass it to the step that runs `pulumi`. In GitHub Actions:

<CodeBlock language="yaml">
  {`- name: Deploy
  run: pulumi up --yes --stack prod
  env:
    PULUMI_ACCESS_TOKEN: \${{ secrets.PULUMI_ACCESS_TOKEN }}
    DATABUDDY_API_KEY: \${{ secrets.DATABUDDY_API_KEY }}`}
</CodeBlock>

`DATABUDDY_API_KEY` and `DATABUDDY_API_URL` are read from the environment of the `pulumi` process (your shell, CI job, or Automation API `envVars`), not from variables set inside your program.

Requests run at most 8 at a time and retry automatically when the API is rate limiting, so large stacks stay within your key's [rate limits](/docs/api/rate-limits).

## Configuration

| Setting | Stack config | Environment variable | Default |
|---------|--------------|----------------------|---------|
| API key | `databuddy:apiKey` | `DATABUDDY_API_KEY` | Required |
| API URL | `databuddy:apiUrl` | `DATABUDDY_API_URL` | `https://api.databuddy.cc` |

Stack config wins when both are set. Point `databuddy:apiUrl` at your own API if you self-host Databuddy.

## Limitations

- **No import**: monitors and status pages that already exist in the dashboard can't be adopted. Delete them there and let Pulumi create them, or leave them out of code.
- **TypeScript and JavaScript only**: the provider runs in Pulumi programs written in TypeScript or JavaScript.

## Troubleshooting

| Error | Fix |
|-------|-----|
| `Missing Databuddy API key` | Run `pulumi config set --secret databuddy:apiKey <key>` with Pulumi 3.216 or newer, or export `DATABUDDY_API_KEY` before running `pulumi` |
| `API key missing required scope` | Add the four monitor and status page scopes to the key |
| `Monitor already exists for this URL` | Another stack or a dashboard monitor uses this URL. If you renamed the resource, add `aliases` |
| `This website already has a monitor` | Each website can have one monitor. Remove the other one or drop `websiteId` |
| `Slug is already taken` | Status page slugs are unique across every account. Pick another one |
| `was redirected ... Set databuddy:apiUrl` | `databuddy:apiUrl` points at a URL that redirects. Use the API's final URL |
| `Function serialization is not supported when using bun` | Set `runtime: nodejs` in `Pulumi.yaml` |
| `fetch failed` behind a corporate proxy | Export `NODE_USE_ENV_PROXY=1` (Node 22.21 or newer) with `HTTPS_PROXY`. Behind TLS inspection, export `NODE_EXTRA_CA_CERTS` with your CA bundle |
